# Architecture

A production-scale system for managing medical DICOM CT data and their
annotations. This document is the durable record of the design decisions
behind the scaffold in this repo.

## Scope and scale

- Data: medical DICOM CT studies (not industrial CT, not a PACS replacement).
- Scale target: 10k-100k studies. No DB partitioning needed at this size;
  standard B-tree indexes on UIDs are sufficient.
- Annotation types are intentionally not finalized yet -- the schema is
  polymorphic (see below) so new types can be added without a migration.
- A dedicated annotator client (DICOM viewer for drawing annotations) is
  explicitly out of scope for this phase. Only the data-management layer
  (ingestion, data browsing, annotation backend, admin) is being built now;
  the viewer is a separate, later effort with its own API.

## Components

                                            |

        |               |                  |                  |               |

 |  Keycloak   | | Ingestion   |   |    Data      |   | Annotation   | |   Admin     |
 | (Auth/OIDC) | |  Service    |   |  Service     |   |  Service     | |  Service    |
 +-------------+ +------+------+   +-------+------+   +-------+------+ +------+------+

                        +------------------+---------+--------+---------------+
                                                       |
                        +------------------------------+------------------------------+
                        |                                                             |
                 +------+-------+                                            +--------+-------+
                 |  PostgreSQL  |                                            |  Object Store   |
                 |  metadata +  |                                            |  (MinIO/S3)     |
                 |  annotations |                                            |  DICOM pixels   |
                 |  + audit log |                                            +-----------------+
                 +------+-------+
                        |
                 +------+-------+
                 | Redis+Celery |   <- async DICOM ingestion (worker pool)
                 +--------------+

Four independent backend services, split by load profile: ingestion is
batch/IO-heavy, data-query is read-heavy, annotation is write-heavy
transactional, admin is low-volume. Each scales independently in
Kubernetes. All four validate the same Keycloak-issued JWT; none manage
passwords or sessions themselves.

| Service | Responsibility |
|---|---|
| `ingestion-service` | Accepts DICOM uploads, orchestrates async processing (Celery) |
| `data-service` | Read-only browsing of studies/series/instances, presigned pixel data URLs |
| `annotation-service` | Annotation create/list/review workflow |
| `admin-service` | Projects, project memberships, de-identification profile management |

## Storage layer (custom, not a PACS)

No Orthanc/PACS layer -- deliberately custom:

- **Object storage** (MinIO self-hosted / S3 in the cloud): raw DICOM pixel
  data, keyed as `{StudyInstanceUID}/{SeriesInstanceUID}/{SOPInstanceUID}.dcm`.
  Binary data never enters Postgres.
- **PostgreSQL**: structured metadata -- `patients` (pseudonymized),
  `studies`, `series`, `instances`. Populated by the ingestion worker via
  `pydicom` header parsing.
- Pixel data is served via short-lived **presigned URLs** generated by
  `data-service`, not proxied through the API.

See `libs/shared-models/shared_models/models.py` for the full schema (this
is the single source of truth -- read it rather than trusting this
document to stay perfectly in sync).

## Annotation schema: polymorphic by design

Since annotation types are still open, the schema avoids hardcoding any
specific type:

- `annotation_types`: registered types (e.g. `bbox`, `segmentation_mask`,
  `label`), each with a JSON Schema used to validate payloads.
- `annotations.payload` (JSONB): small geometry (points, boxes, labels)
  stored directly. Large binary data (e.g. segmentation masks) is stored in
  object storage instead, with `payload` holding just a storage key
  reference -- keeps Postgres fast for both reads and writes.

Adding a new annotation type means inserting a row into `annotation_types`
with its JSON Schema; it does not require changing `annotation-service` or
running a schema migration.

## Versioning: two layers

1. **Annotation-level audit trail.** Edits never mutate a row in place --
   they insert a new `annotations` row with `parent_version_id` pointing at
   the previous version. Every change is attributable and reversible.
2. **Dataset-level immutable snapshots.** `dataset_snapshots` +
   `dataset_snapshot_items` reference a specific set of
   (study, annotation version) pairs at a point in time -- e.g. "v1 dataset
   for model training". This is a manifest, git-commit-style, not a data
   copy, so it stays cheap even at scale.

## Access control: project-scoped RBAC

Two-tier authorization:

- A global Keycloak realm role `admin` grants access to everything.
- Everyone else is checked against `project_memberships` (`project_id,
  user_id, role`) for a role scoped to the specific project being accessed.
  Roles: `admin`, `data_manager`, `annotator`, `reviewer`, `viewer`.

Every `study` belongs to exactly one `project`. This lookup is implemented
once in `libs/shared-auth` (`require_project_role`) and reused by every
service, rather than reimplemented per service.

This was chosen over Keycloak fine-grained authorization (which would push
per-project access rules into Keycloak itself) because the simpler
approach -- a plain join table queried by each service -- is easier to
reason about, test, and review at this scale.

## De-identification: admin-configurable, not hardcoded

Rather than a fixed DICOM PS3.15 profile baked into code, de-identification
is data-driven:

- `deidentification_profiles`: named, admin-editable profiles, one of which
  can be assigned per `project`.
- `deidentification_rules`: per-DICOM-tag rules (`keep` / `remove` /
  `replace_fixed` / `hash`) within a profile.
- The ingestion worker (`services/ingestion-service/app/deidentify.py`)
  looks up the active profile for a study's project and applies it before
  the file is written to object storage.

**Open item:** the exact rule sets (which tags, what strategy) are a legal/
compliance decision, not a technical one, and are deliberately left for the
admin to configure per project rather than assumed by this codebase.

## Ingestion pipeline

1. `POST /ingestion/projects/{project_id}/upload` stages the file and
   enqueues a Celery job; returns a `job_id` immediately (async, not
   blocking).
2. Worker (`app/pipeline.py`):
   - Parses the DICOM header (`pydicom`), validates required tags
     (`StudyInstanceUID`, `SeriesInstanceUID`, `SOPInstanceUID`).
   - **Duplicate check**: an existing `sop_instance_uid` is a no-op
     ("duplicate"), not an error -- makes re-uploads and partial retries
     idempotent.
   - Applies the project's de-identification profile.
   - Uploads pixel data to object storage.
   - Upserts `patient` / `study` / `series`, inserts `instance`, in one
     transaction.
3. One instance's failure does not fail the whole batch. Transient errors
   (network/storage) retry with backoff (`app/tasks.py`); permanent
   validation errors (`DicomValidationError`) do not retry.

## Kubernetes topology

See `infra/k8s/`. Namespace `ct-platform`; one Deployment+Service per
backend service, plus a separate `ingestion-worker` Deployment running the
same image as `ingestion-service` but as a Celery worker (scaled
independently -- ingestion is CPU/IO-heavy batch work, unlike the
request/response API). Ingress path-routes `/api/{ingestion,data,
annotation,admin}` to the corresponding service and `/auth` to Keycloak.

**Deliberately not included in `infra/k8s/`:** Postgres, Redis, MinIO,
Keycloak. For local dev, `docker-compose.yml` covers these. For a
production cluster: managed Postgres (RDS/Cloud SQL) or the CloudNativePG
operator instead of a hand-rolled StatefulSet (backup/HA/patching are not
worth re-implementing); managed Redis or an operator; cloud S3 or the MinIO
Operator; the Keycloak Operator with its own HA Postgres. This is deferred
until the target environment (cloud vs. on-prem) is decided.

## Code organization and review requirements

This codebase is AI-generated (with Claude) and must be verifiable by
humans and by Codex. That drove several structural choices, not just the
ones above:

- **Independently separable, independently testable units.** Each service
  under `services/` has its own `README.md`, its own `requirements.txt`,
  its own `Dockerfile`, and its own `tests/` runnable without the other
  services, without Celery, without a live Keycloak, and (for most tests)
  without a live Postgres.
- **Shared logic lives in `libs/`, not copy-pasted.** `shared-models`
  (schema) and `shared-auth` (JWT + project-role checks) are each
  independently versioned packages, not services -- so a schema change or
  an auth-logic fix happens in exactly one place.
- **English comments and docstrings throughout**, regardless of the
  working language used to discuss the project.
- **No speculative abstraction.** Endpoints and modules implement exactly
  what the current design calls for; nothing is built ahead of a concrete
  requirement (e.g. the annotator viewer client is not scaffolded, since
  it was explicitly deferred).

## Deliberately deferred / open items

- Annotator DICOM viewer client (separate API, later phase).
- Exact de-identification rule sets (compliance decision).
- Target deployment environment: cloud vs. on-prem Kubernetes.
- CI pipeline (build/test/push container images).
- Dataset snapshot creation/export endpoints (schema exists; no API yet).
- Initial Alembic migration has not been generated -- run it against a
  running Postgres per `infra/migrations/README.md`.
